# Cross-Process Concurrency: Single-Writer Lockfile + Read-Only WAL-Tailing Readers

## Summary

imbh supports one read-write writer process plus N read-only reader processes over the same directory, with near-real-time reader visibility. The writer owns the directory via an exclusive advisory `writer.lock`; readers open with `Db::open_read_only` and answer each query from a fresh point-in-time snapshot (manifest segments union the live WAL tail) made visible for free through the shared OS page cache. It is explicitly not multi-writer, not MVCC, and not cross-process point deletes.

## Key Facts

- Scope: single writer + N read-only readers, near-real-time via WAL tailing. Not multi-writer / MVCC / cross-process point deletes.
- `writer.lock` is an exclusive advisory lock via `fs4::fs_std::FileExt`, acquired inside `Storage::open`, released on drop / process exit. `fs4` was already a transitive dep through Tantivy, so **zero net new crates** (`Cargo.lock` fs4 entry unchanged).
- A reader never needs the writer's RAM: everything queryable is already on disk as two crash/torn-tolerant artifacts (atomic-rename manifest + checksummed append-only WAL). Cross-process visibility of just-appended WAL bytes is free via the OS page cache. fsync is durability, not visibility. The feature needed **no new IPC**.
- Near-real-time reads require the WAL enabled. `WalMode::Off` readers get segment-only (seal-interval) freshness; a WAL-off reader is rejected by default (see the WAL-off guard).
- `Db` is a concrete struct shared as `Arc<Db>`; `open()` / `open_async()` / `open_read_only()` return `Arc<Db>`.
- `flock` (what `fs4` uses on unix) is per-open-file-description, so a second same-process open contends too, making an in-process double-open a valid stand-in for a second process. Phase 4 still added a real two-process test.
- Completed across four phases (all footprint-neutral, no new crates in any phase); only the Phase 3 perf item remained, later closed with the incremental cursor + refresh knob.

## Details

### Single-writer lockfile + read-only WAL-tailing readers (Phases 1-2)

- **`imbh-core`**: `Access` enum (`ReadWrite` default / `ReadOnly`) in `config.rs`; `ConfigKind::ReadOnly` + `Error::read_only()` (a `is_user_error` leaf). The reserved `OpenKind::LockHeld` / `Error::lock_held` gained a real call site.
- **`imbh-storage`**: `writer.lock` exclusive advisory lock via `fs4::fs_std::FileExt`, acquired inside `Storage::open` (signature kept stable, no test ripple), released on drop / process exit. New `Storage::open_read_only` (no lock, no WAL append handle, `read_only` flag; `ingest*` refuse). New `DiskSnapshot` + `read_disk_snapshot(dir)` implementing the **manifest re-check bracket** (read manifest, scan WAL, re-read manifest, retry if watermark moved; bounded by `SNAPSHOT_RECHECK_TRIES`).
- **`imbh` facade**: `Db::open_read_only` / `DbBuilder::access`. Open branches on access (readers skip replay-into-writer and skip maintenance). `collect_with_stats` branches to `reader_tables`, which rebuilds a fresh snapshot per query: manifest segments union WAL tail, the tail replayed into a throwaway `Storage::in_memory` via the factored `replay_record` (shared with open-time recovery). Write methods go through `ensure_writable()`.

The re-check bracket is the whole reader-correctness story and it is cheap: because the writer reclaims WAL only *after* the superseding manifest is durable, a watermark stable across the bracket guarantees segments (`lsn <= W`) and tail (`lsn > W`) are disjoint (no double-count) and every tail frame still exists (no drop).

### Db made a concrete struct; handles shared as Arc<Db>

`Db` was a `#[derive(Clone)] struct Db { inner: Arc<Inner> }` cheap-clone handle; it is now the **concrete** struct (`Inner`'s fields merged in, `Inner` deleted), no longer `Clone`. `open()` / `open_async()` / `open_read_only()` return `Arc<Db>`, and consumers hold `Arc<Db>`. Runtime cost is identical (the single `Arc` moved from inside the type to the caller), but the type no longer dictates a sharing strategy and a consumer that already needs `Arc<Db>` avoids a double `Arc`.

Mechanics: handle-returning methods (`logs`/`traces`/`metrics`/`attrs`/`sql`/`sql_with_params`/`export`/`blocking`) take `self: &Arc<Self>` and hand `Arc::clone(self)` to the `'static` `LogsApi`/`Query`/`BlockingDb`; the direct ops stay `&self` and reach through the `Arc` deref. `Query`'s field `inner: Arc<Inner>` became `db: Arc<Db>`; the maintenance worker's `Weak<Inner>` became `Weak<Db>`; `reader_tables(&Inner)` became `reader_tables(&Db)`. Consumers (`imbh-server`, `imbh-otel-exporter` x3, `imbh-tracing::DbLayer`, the `replay-otlp-file` example, and two facade test helpers) changed `Db`/`&Db` to `Arc<Db>`/`&Arc<Db>`; every `db.clone()` kept working as `Arc::clone`.

- The one genuine hazard is a `&self` method that internally builds a `Query`/typed API: it cannot call `self.sql()` anymore (no `Arc` in hand). Exactly one existed, `Db::export` (it runs a `SELECT` internally), which became `self: &Arc<Self>`. Worth grepping `self\.sql(`/`self\.logs(` before committing to the receiver set.
- Method resolution does the ergonomic heavy lifting: callers like `self.db.sql(...)` and `db.logs()` auto-ref the `Arc<Db>` place to the `&Arc<Self>` receiver, and `&self` methods reach through `Arc` deref, so most call sites compiled unchanged.
- Field-flatten vs field-retype: for `impl Db`, `self.inner.X` flattened to `self.X`; for `Query`, retyping the field was cleaner than flattening. A blind global `self.inner.` to `self.` would have broken `Query`. Watch multi-line field chains (`self\n.inner\n.storage`) which a line-oriented grep/replace misses.

Footprint unmoved: `imbh` facade still **275** crates (a pure internal-shape change).

### Phase 3: read-during-delete retry + atomic writer snapshot (and a mid-seal drop window)

- **Read-during-delete retry-on-missing** (`imbh/src/lib.rs`). Retention/`compact()` on the writer can unlink a segment between the instant a read-only query captures its path and the instant DataFusion opens it. The read-only branch of `collect_with_stats` loops up to `READER_QUERY_TRIES` (4): it records the snapshot's segment paths (`snapshot_paths`, Parquet + `.tidx`), and if `run_sql` errors **and** any of those paths has since vanished, it re-derives the snapshot from the current manifest (which no longer lists the file) and retries. A failure with every path still present is returned as-is. Detecting the race by "did a snapshotted path disappear" rather than by parsing DataFusion's error text keeps it robust.
- **Atomic writer query snapshot** (`imbh-storage`, `imbh` facade). `Storage::query_snapshot` captures every table's buffer + segments under one `inner` lock; `imbh::writer_tables` consumes it, replacing the old per-table `buffer_snapshot()`-then-`segments()` calls that crossed multiple lock acquisitions and could double-count across a background seal.

**A single lock is *not* sufficient: `seal` has an off-lock drop window.** The design doc claimed "snapshot buffer+segments under one lock" closes the intra-process race. Building and testing under concurrent seal proved otherwise: `seal` empties the buffer under the lock, writes the Parquet segment **off-lock** (deliberate, so ingest isn't blocked during encoding), then re-locks to register it. In that window the rows are in **neither** the buffer nor a segment, so a single-lock `buffer union segments` snapshot transiently **drops** them. The test caught it immediately: a writer-path `count(*)` fell `4 -> 1`. This is a *drop*, distinct from the *double-count* the earlier review named, and it was latent in the old two-lock path too.

- **Fix:** `seal` stages the taken batches in a new `Inner::sealing` map (keyed by a per-seal generation id, so concurrent seals with disjoint batch sets don't collide) for the duration of the off-lock write; `query_snapshot` unions `buffer union sealing union segments`. The staging entry is removed under the *same* lock that registers the segment (and before `persist_manifest`, so a manifest write error still leaves the rows visible in the in-RAM segment rather than double-counted), and on the seal error path when batches are handed back to the buffer. Batch clones are cheap: Arrow columns are `Arc`-shared, so staging is a pointer copy, not a data copy.
- **Why the cross-process reader was already immune:** it reads manifest union WAL-tail, and the WAL still holds the rows (frames `> watermark`) until the seal bumps the watermark and reclaims them, so the reader sees them in the tail throughout the seal. Only the writer's `buffer union segments` path had the gap. This argues the WAL-tail snapshot is the more robust model.

### Phase 4: two-process integration test + doc sweep

A true two-*process* integration test lives in `crates/imbh/tests/cross_process.rs`. The prior cross-process tests used two `Db` handles in one process (valid, since `flock` is per-OFD); this test spawns a real second OS process.

- **Mechanism (no helper binary, no network).** The single `#[test]` branches on an `IMBH_XPROC_ROLE` env var. The parent re-execs `std::env::current_exe()` (the test binary) with `--exact cross_process_writer_and_reader` + `IMBH_XPROC_ROLE=writer`, so the child runs *only* this test, hits the env branch, plays the writer, and exits 0 (a passing test). No env means the process is the reader/parent. This is the libtest re-exec pattern; setting the env in the child before it spawns anything prevents a fork bomb.
- **What it asserts.** (1) Cross-process `writer.lock` rejection: while the writer process lives, a second read-write open fails with "lock held"; once it exits, a fresh read-write open succeeds (OS releases the lock on exit, no stale-lock logic). (2) Page-cache WAL freshness: the reader *process* sees rows the writer just ingested, before/independent of any seal. (3) No drop / no double-count: `count(*) == count(DISTINCT body)` and a monotonic non-decreasing count on every poll, terminal `== N`, while the reader queries across the writer's live `flush()`es (seal + WAL reclaim).
- **Determinism.** The lock-held vs lock-released checks would otherwise race the writer's lifetime, so the writer waits on a `.parent-done` sentinel file before exiting: the parent does its lock-held check while the writer is guaranteed alive, writes the sentinel, then validates release. The writer spreads ingest with a 2 ms/row sleep so the reader's polls genuinely interleave with active writes. Runs in ~2.4 s.

The libtest `--exact` re-exec is the cheapest path to a real multi-process test in a no-external-deps suite (cost is one env var + a role branch, plus passing `--test-threads=1` so the child runs exactly one test; `catch_unwind` + always-create-sentinel + `child.wait()` keeps a panicking parent from leaking the child). A sentinel-file handshake beats sleeps for lifetime-ordered cross-process assertions.

Doc sweep to the built state: ARCHITECTURE.md §5 (read-during-delete handled; "queries see buffer + segments, atomically" rewritten around `query_snapshot` + the off-lock seal window), §7 (mutable-buffer + seal-path bullets describe `Inner::sealing` staging), §14 (the "reader reads a just-deleted segment" risk marked Mitigated; added an intra-process seal-vs-query row). OVERVIEW.md §3 notes the snapshot is consistent under concurrent seal/reclaim/retention with bounded retry.

### WAL-off reader guard (closing the silent-staleness gap)

A reader against a **WAL-off** writer silently got only seal-interval freshness with no way to know (a reader process can't see the writer's in-RAM `WalMode`). Fix: make the mode knowable from disk and guard on it.

- **Marker.** A read-write open writes a small `db.info` file (`wal_mode\t<off|interval|always>`, temp -> rename so a reader never sees a torn line) right after taking the writer lock (`imbh-storage`). Best-effort (a reader hint, never a writer correctness input), so any I/O error is swallowed. `cleanup_orphans` already leaves non-`parquet`/`tidx`/`tmp` files alone, so `db.info` survives and a crash-left `db.info.tmp` is reaped as a stray temp.
- **Reader detection.** `imbh_storage::writer_wal_disabled(dir) -> bool`: `true` only when the marker is present *and* says `off`; missing/unparseable means `false` (unknown never rejects, so pre-marker DBs open exactly as before).
- **Guard.** `Db::open_read_only` (and `Access::ReadOnly` via the builder) returns the new `Error::reader_wal_disabled` (a user-facing Config error) when the writer's WAL is off, unless the caller opts in with `DbBuilder::allow_stale_reads()`. New `ConfigKind::ReaderWalDisabled` + constructor in `imbh-core`.

**Design choice: reject-by-default + opt-in, not warn or hard-fail.** A warning is invisible without an opt-in subscriber (tracing off by default). A hard, unconditional failure would break legitimate offline/static reads of a cleanly-closed WAL-off DB. Reject-by-default with an explicit `allow_stale_reads()` escape hatch makes the reduced-freshness contract a conscious choice, fitting `open_read_only`'s implicit promise of near-real-time cross-process reads. (Probing writer liveness via the lock to only reject a *live* WAL-off writer was considered and dropped as racy; the persisted marker is the honest, simple signal.)

### Phase 3 WAL-tail perf: incremental reader cursor + refresh knob

A read-only handle re-read and re-decoded the *entire* WAL tail on every query (`read_disk_snapshot` -> `wal::read_all_frames`, O(WAL) per query). Two complementary, opt-in-safe changes (default behavior unchanged):

**Incremental WAL-tail cursor (imbh-storage).** New `WalTailCursor` holds a per-segment byte offset (always a clean frame boundary), a running max-LSN (seeds strict monotonicity across new bytes and segment boundaries), and the accumulated live tail. `read_disk_snapshot_incremental(dir, &mut cursor)` reuses it: `cursor.advance` scans only bytes appended since the last call (`read_segment_from` seeks to the offset and reads to EOF, O(new bytes) not O(segment)), and each refresh prunes the sealed prefix (`lsn <= watermark`, now durable in a segment). `scan_frames` returns the consumed byte count so a torn/mid-append tail resumes exactly once the writer completes it. The manifest re-check bracket is unchanged, so consistency (segments `lsn <= W` union pending `lsn > W`, disjoint + complete) is identical to a fresh scan. `read_disk_snapshot` became a thin wrapper over a fresh (default) cursor, proving the cursor is a pure performance cache, not a behavior change.

**Refresh knob (imbh-core + facade).** New `Refresh::{OnQuery, Ttl(Duration), Manual}` (in `imbh-core::config`, re-exported) on the read-only builder (`DbBuilder::refresh`). Backed by a new `Db.reader_cache` (`Mutex<ReaderCache>` = the persistent incremental cursor + the last-built `Vec<TableInput>` + its build `Instant`): `OnQuery` (default) rebuilds every query but through the persistent cursor, so even the near-real-time path scans only new bytes; `Ttl(d)` reuses the cached tables until `d` elapses; `Manual` pins the snapshot until an explicit `Db::refresh()` (+ `BlockingDb::refresh`). `reader_tables` moved onto `Db` as a cache-aware method taking a `force` flag; the read-during-delete retry passes `force=true` after a failed attempt so a cached (`Ttl`/`Manual`) snapshot can't loop on a segment the writer just unlinked (the rebuild re-derives from the current manifest, which no longer lists it). `TableInput` gained `#[derive(Clone)]` (all fields are `Copy`/`Arc`/small-`Vec`, so cloning a cached set is cheap).

Invariants:
- Default is still poll-on-every-query near-real-time (`Refresh::OnQuery` is `Default`); the knob is purely additive. `Ttl`/`Manual` trade a bounded, opt-in staleness for collapsing a query burst onto one WAL scan.
- `refresh()` is sync (building `TableInput`s is non-async), no `block_on` in `BlockingDb::refresh`; a no-op returning `Ok` for read-write / in-memory handles (they query live buffers under the lock).
- `reader_stats` left on the fresh `read_disk_snapshot`: stats aren't the hot path and don't build `TableInput`s.
- Lock is never held across `.await`: `reader_tables` (sync) acquires/releases the cache mutex before `run_sql(...).await`, so a `std::sync::Mutex` is correct.

New public surface: `Refresh`, `Db::refresh`/`BlockingDb::refresh`, `imbh_storage::{WalTailCursor, read_disk_snapshot_incremental}`.

## Pitfalls

- **Silent staleness (WAL-off readers).** Near-real-time reads require the WAL. A `WalMode::Off` writer gives readers only segment-only (seal-interval) freshness. A reader process can't see the writer's in-RAM `WalMode`, so the `db.info` marker + reject-by-default guard (`allow_stale_reads()` to opt in) is what stops a reader from silently reading stale data.
- **Mid-seal drop window.** A single lock over `buffer union segments` is NOT sufficient for the writer path: `seal` empties the buffer under the lock but writes the segment off-lock, so mid-seal the rows are in neither buffer nor segment (a *drop*, distinct from double-count, latent in the old two-lock path). Only `Inner::sealing` staging (unioned into `query_snapshot`) closes it. The reader path was always immune because the WAL holds the rows until the watermark bumps.
- **Read-during-delete.** Retention/compaction can unlink a segment between a read-only query capturing its path and DataFusion opening it. Handled by bounded retry (`READER_QUERY_TRIES` = 4) that re-derives the snapshot from the current manifest only when a snapshotted path has actually vanished; an error with every path still present is returned as-is (never masked). With `Ttl`/`Manual` refresh, the retry passes `force=true` so a cached snapshot can't loop on an unlinked segment.
- **Double-count vs disjointness.** Reader correctness depends entirely on the manifest re-check bracket keeping segments (`lsn <= W`) and tail (`lsn > W`) disjoint and complete. The incremental cursor must preserve this exactly (it does; `read_disk_snapshot` is a thin wrapper proving equivalence).
- **`Ttl`/`Manual` staleness is opt-in and bounded.** `OnQuery` (default) stays near-real-time; `Ttl(d)`/`Manual` deliberately trade bounded staleness for fewer WAL scans. `Manual` pins until `Db::refresh()`.
- **Testing gotchas.** `Db`/`Storage` aren't `Debug` (match on the result, don't `unwrap_err`). The crate's `tokio` has no `rt-multi-thread`, so concurrency tests drive one current-thread runtime per OS thread. For the two-process re-exec, set the role env in the child before it spawns anything (prevents a fork bomb) and pass `--test-threads=1`.
