# imbh-tui Explorer and the gen-demo-db Demo-Data Generator

## Summary

`imbh-tui` is the reference terminal explorer over a read-only imbh database: a route-based, browser-history navigation model with a Midnight-Commander-style menu bar, a universal focus ring, and dedicated viewers for traces, logs, and metrics driven by PromQL/LogQL/TraceQL. `examples/gen-demo-db` is a footprint-isolated example binary that populates a database with realistic, wall-clock-anchored metrics, correlated logs, and deep cross-service traces so the explorer has something to render. Almost all of `imbh-tui` lives in one file (`crates/imbh-tui/src/lib.rs`); its central discipline is that `draw` is a pure `&App` function, so every render-time bound is published back to the input handler through interior mutability.

## Key Facts

- `imbh-tui` is 27 modules under `crates/imbh-tui/src/` (it was one 9,384-line `lib.rs` until the split; older notes saying "one file" are stale). The split axes: `app/` (state + the state machine, its inherent impl spanning `mod`/`nav`/`views`/`window`/`catalog`/`completion`), `ui/` (rendering, never mutating `App`), plus `waterfall`/`format`/`keys`/`model`/`fetch`/`tasks`/`runtime`/`terminal`/`mascot`. Tests live next to what they exercise; shared fixtures in `#[cfg(test)] mod testutil`. The event loop runs `flavor = "current_thread"`, so `App` is never shared across threads and `Cell`/`RefCell` are safe.
- `draw` takes `&App`; motion/scroll state must advance in the run loop (which holds `&mut app`) *before* draw. Render-time geometry flows back via interior mutability (`Cell<u16>` for `max_scroll`/`page_rows`, `RefCell<Option<ChartGeometry>>` for the chart).
- `Db::{logs,traces,metrics}()` take `self: &Arc<Self>`, not `&self` — a free helper calling them must take `&Arc<Db>`, not `&Db` (deref coercion does not help; `E0599` otherwise).
- Navigation splits two orthogonal axes: `Route` (which view; part of browser history) vs `Mode` (transient input overlay: Menu/Editing/TimeRange/Absolute; never in history). `screen()` derives from `route`.
- Back/Forward is a two-stack machine (`back`/`forward: Vec<NavEntry>`); every forward navigation does `back.push(current); forward.clear()`.
- Focus ring stops: `[Menu(0..4), TimeRange, Query?, Primary]`. Arrows never drive the ring; Tab/Shift+Tab do. Focus is transient chrome, reset to `Primary` on navigation, never in history.
- The whole TUI funnels time through one seam: `eval_window(options) -> (start, end, EvalRange, EvalLimits)`; rolling vs absolute is a single branch there (`Options.window: Option<(i64, i64)>`).
- Fixed-width text columns MUST clamp/measure by display width (`unicode-width`: `UnicodeWidthStr`/`UnicodeWidthChar`), never `char`/scalar count — CJK glyphs are 2 cells.
- Decorative glyphs in a width-measured line MUST be East-Asian-width *unambiguous* (`width(c) == width_cjk(c)`). Verified safe: `⬤` U+2B24, `⏲` U+23F2, `▾` U+25BE, `▸` U+25B8. Ambiguous (avoid): `●` U+25CF, `•` U+2022, `·` U+00B7, `▼` U+25BC, `▶` U+25B6.
- `chrono`/datetime crates are kept *out* of the terminal dependency graph — UTC formatting/parsing is hand-rolled via Howard Hinnant's `civil_from_days` / `days_from_civil` (shared `719_468`/`146_097` constants). `unicode-width` and `rand` (`small_rng`) are the only notable direct deps added, both already transitively present or acceptable because `imbh-tui` is not core.
- `gen-demo-db` is an *example* crate: `opentelemetry-proto` + `prost` live only there, never entering the `imbh` facade graph. Deterministic via a fixed-seed splitmix64 PRNG (no `rand` subtree in the generator).
- `--ascii` renders a genuinely pure-ASCII UI; a single `Glyphs::new(ascii)` bundle plus an `ASCII_BORDER` `border::Set` is the one source of truth. Test `ascii_mode_renders_only_ascii_across_the_ui` asserts every emitted cell `is_ascii()`.
- Every exit path (normal teardown, a partial `enter()` failure, a panic) goes through one `restore_terminal` helper; the panic hook that calls it is chained to the previous hook and installed once via an `AtomicBool` CAS.

## Details

### Navigation and chrome

**Route-based router + browser back/forward.** The horizontal view chains evolved twice: first a spatial chain (`→` deeper / `←` back), then genuine browser Back/Forward, then a typed `Route` router. The distinguishing test: if `→` can reach something the user has not visited, it is a *spatial affordance wearing the arrow keys*, not Back/Forward — under browser semantics `→` only redoes a Back, and forward-to-new is an explicit action (Enter / `t` / a screen key). This resolved the log-detail→trace inconsistency: opening the trace is a forward *navigation* (Enter) that Back can return from. The two-stack machine (`back`/`forward: Vec<NavEntry>`) must capture the *departing* view **before** mutating to the destination, and — when the destination might not open (e.g. an empty series list) — capture first and record only on success via `push_entry(entry)`, or a no-op Enter silently clears the redo stack. A `Route` enum earns its keep by making the detail *data* part of view identity: `Route::{LogDetail{record}, MetricDetail{detail}}` means history captures the payload for free via one `route: self.route.clone()`, replacing hand-snapshotting `screen` + `Mode` + `Option<LogRecord>` + `Option<MetricDetail>` field-by-field. Splitting "which view" (Route, in history) from "which input overlay" (Mode, never in history) is the distinction that made the whole thing tractable. Non-modal = `draw` always renders the menu bar then dispatches only the *content area* by route (detail views render there, not full-frame); `handle_key` runs transient-mode overlays first, then `handle_detail_key` consumes *only* the detail's own keys and returns `None` for the rest, so history nav, `F9`, `1`-`4`, and `t` all work from inside a detail. Mechanical `screen` field → `screen()` method migration across ~40 sites used `perl -pe 's/\.screen\b(?!\s*[=(])/.screen()/'` but the `[=(]` class also matched the first `=` of `==`, leaving comparisons unconverted — after a scripted rename, diff the *count* of remaining raw references and eyeball survivors.

**Universal focus ring / tabstops.** `Tab`/`Shift+Tab` move a visible focus highlight; arrows are untouched (they always drive the main list). Modelled as `Focus { Menu(usize), TimeRange, Query, Primary }` on `App`, reset to `Primary` on every navigation (`switch_screen`, `restore_nav`) and kept out of `NavEntry` — exactly like `mode`. The ring cycles in reading order: the four screen menu items, the time selector, then the content panes: `[Menu(0..4), TimeRange, Query?, Primary]`. A `&'static [Focus]` ring slice works with the payload-carrying `Focus::Menu(0)` because it is a const expression. The query stop only exists where a query pane does (`App::has_query`: not Overview, not a detail route); rather than scrub `focus` eagerly, `effective_focus()` snaps a stored `Query` to `Primary` whenever the current view has no query pane — a read-time normalizer read by both the renderer (immutable `&App`) and `focus_advance`, so the highlight and `Enter` can never target an off-screen pane. `Tab`/`BackTab` were already consumed in Editing/AbsoluteRange/Menu modes but dead in `Mode::Normal`, so the ring slots in with zero conflict. Activation is shared, not duplicated: `Enter` on the time selector / query pane point at extracted `open_time_range` / `begin_editing` free functions (the same as `t`/`e`), so entry points can't drift. The highlight reuses existing channels — every content pane is already a `Block` with `Borders::ALL`, so a one-line `.border_style(focus_border(...))` (bold cyan when focused) marks it uniformly across query pane, all three primary render paths, and the detail-route bodies.

**Active-vs-focus + colour-as-a-channel.** *Active* (you-are-here current screen) and *focused* (the ring cursor) are different facts and had collided on one cyan highlight. Split into two chips: a solid **white** chip for the active screen and a **black chip with cyan text** for the focus cursor; both can show at once on different items, cursor wins when they coincide. General rule: if two independent states can be true of one widget, they need two visual channels, not one shared highlight. Colour is a scarce channel — pick one meaning per hue and defend it. **Cyan means focus** everywhere (it already drew focused-pane borders), so the whole bar turns cyan the instant the ring lands on any bar item (`menubar_focused` = F9 menu open, or the time picker open, or `focus ∈ {Menu, TimeRange}`), and the *default* bar moved off cyan to **blue** (ready) / grey (loading). When a new signal wants a colour already spoken for, re-home the old signal rather than overload the hue. Two terminal-colour gotchas: `BOLD` + `Color::Black` renders as bright-black (grey) on many terminals — the " IMBH " brand washed out; fix was to drop `BOLD`, not change the colour (bold silently shifts hue on dim base colours, so never rely on bold black for contrast). And ratatui's `Gray` is ANSI 7 (the terminal's light "white") while `DarkGray` is ANSI 8 (bright-black, the *recessed* one) — for "de-emphasise this", reach for `DarkGray`, not `Gray`; the ANSI names invert the intuition. Recolour off actual state (the `Mode::TimeRange`/`AbsoluteRange` modes) not a flag someone must remember to set, so opening the picker via any path lights the bar correctly.

**F9 menu bar + horizontal view chains.** `F9` activates the menu bar (a flat `menu_cursor: usize` over `MENU_LEN = ORDER.len() + 1`, spanning the four screens plus a trailing time-range item; `menu_screen()` returns `Some(screen)` or `None`; `Screen::next/prev` became dead code and were deleted, `index()` survives to seed the cursor). Freeing the arrow keys from direct screen-switching unlocked the horizontal view chains: `→` forward/deeper, `←` back, Enter/Esc as aliases at each hop. Lesson: when a key is overloaded, narrow its old job so the freed capacity serves a new orthogonal axis — arrows = cross-view (horizontal), Up/Down = within-view (vertical). Any UI state attached to a periodically-rebuilt list needs an identity key to survive the rebuild: the catalog tree is rebuilt from every fresh snapshot (`build_metric_tree`), so checkboxes/expansion/discovered-dims are carried over *by metric name* (drain old nodes into a `HashMap<name, MetricNode>`, reuse the match, mint fresh nodes only for new metrics) — index position is not the key (rows reorder), the domain name is. Test the preserve-across-rebuild by feeding the *raw* snapshot (re-seed the raw catalog table before the second `build_metric_tree`), not the rendered rows whose first column carries the `▾`/`▸` markers.

**Left/Right as context-sensitive keys.** When the focus ring is on a menu-bar stop (`Focus::Menu(_) | Focus::TimeRange`), Left/Right walk the five menu-bar items (`App::menubar_move`, wrapping over `MENU_LEN`, mirroring the F9 `menu_move`) and `return` early so they never reach history; on a content pane they stay Back/Forward, with Esc an alias for Back. Same physical key, two meanings, disambiguated by focus — put the early-return at the focus layer (which runs *before* `handle_detail_key` and the global match), so the later `KeyCode::Left | KeyCode::Esc => go_back` arm is simply unreachable in that state (no flag, no ordering fragility beyond "focus block first"). Lesson: "never do X" attached to a feature request is usually scoped to *that feature's context*, not a global ban; confirm the scope before ripping a binding out (removing history from the arrows entirely was a wrong build the user then corrected). A binding change is also a documentation change: grep the UI hint strings for the affected key glyphs (`← back`, `→ fwd`, `←→`, `←/esc`) after touching a keymap — a stale hint is a silent correctness bug for the user's fingers.

**One-line MC-style header + deduplicated chrome.** The 3-line bordered header collapsed into a single Midnight-Commander-style menu bar (screen menu left, time-range + clock selector right), branded with a black-hole glyph `⬤`; dropping the borders (`Length(3)` → `Length(1)`) handed two rows back to the results pane. A manually right-aligned bar needs one width function shared by the render and the geometry it publishes: both the filler length and the selector anchor `x` come from the *same* `UnicodeWidthStr`-based `span_width` over the left spans — measure once, or the drawn position and the published dropdown anchor drift apart. Once the header owned the range/clock indicator, three footer fields were redundant and were moved to a single owner each, not kept in sync (a duplicated field is a bug waiting to desync — delete, don't sync). Readiness became the bar's *colour* (a state already ambient is better carried by an always-on-screen channel than a word competing for legend space). Auto-refresh became a `!` flag appended after `range_summary()`, gated on `app.auto_refresh && app.abs_window.is_none()` — an absolute window never moves, so the flag means "this view will keep advancing", not merely "the toggle is on". The footer trimmed to a pure key legend (`q quit · F9 menu · … · e edit`). Caveat: `app.loading` clears fast on a local DB, so the grey "busy" flash can be near-imperceptible — when a transient state maps to a colour, the state may blink faster than a human eye resolves.

**Context-aware query autocompletion.** The caret is always end-of-string (the editor only pushes/pops at the end), so `completion_context(query)` is a suffix classification, not a parser: count `"` (odd ⇒ inside an open quoted value), else find the last `{` after the last `}` (⇒ inside a matcher block), else expression position. It returns the context plus the partial token to match/replace. Context is worth adding even where the vocabulary is empty because it *suppresses* wrong suggestions — returning `Suppressed` for an unquoted value slot removes noise even on Logs/Traces where no label vocabulary is wired; the negative space (what *not* to offer) was most of the UX win. The label vocabulary already existed as a side effect of the catalog tree (`metric_tree`, each `DimNode` = label + values); completion parses the selector metric before the `{`, reads that node's dims, and for a bare `{…}` falls back to the union across all discovered metrics. Lazy-fetch is triggered from the keystroke, applied from async arrival: `completion_dim_request` marks the metric loading and returns `(name, kind)` so the key handler fires `request_metric_dims`; `Update::MetricDims` re-runs `refresh_completion`. Marking `loading` in the *request* (not on arrival) makes it fire at most once per metric. Empty-token behaviour depends on context: expression position waits for one char (metric/function lists are large), but a label context lists its whole small set immediately on `{` or `"` (`matches!(context, Expr | Suppressed) && token.is_empty()` encodes the split). The completion syntax highlighter is one lightweight, keyword-set-parameterized tokenizer serving all three languages (strings / numbers+durations / identifiers+calls / operators / punctuation); it never rejects input, round-trips exactly (a test asserts concatenated spans reproduce the source), and is kept independent of the real `imbh-lgtm` parsers so it can't drift into rejecting valid input.

### Signal viewers

**Traces waterfall.** Tree-indented waterfalls misalign unless the indent lives *inside* the fixed-width name column: `"  ".repeat(depth)` prepended to the whole line pushed the `|bar|` axis 2 cells right per level; fold `indent + name` into one `NAME_W`-cell field so everything left of the first `|` is constant width. General rule for any text column chart: every character left of the plotted axis must sum to a fixed width; tree depth belongs *inside* a clamped field, never as a bare line prefix. `clamp_field` pads/truncates by `unicode-width` cell count (see Pitfalls). A later pass tightened margins and made bars fill the pane: `build_trace_detail(trace, ascii) -> TraceDetail` (originally `build_waterfall`) runs off-thread, emits the structured per-span `Vec<SpanRecord>` the trace detail screen needs alongside the rows, and stores each bar as *fractions of trace duration* (`start`, `frac`) plus precomputed `prefix`/`suffix`; `render_waterfall(&Waterfall, bar_cells) -> Vec<String>` paints them at draw time to whatever cell width the pane has (`bar_cells = pane_width - (1 + WATERFALL_NAME_W) - 2 - WATERFALL_SUFFIX_W`, clamped `>= 1`). Width must be resolved at draw time, not build time — baking a pixel width off the event loop can't reflow on resize; duration-fraction bars widen to the pane (~77 cells at 120 cols vs the old hardcoded 40) and re-flow on the next redraw with no re-fetch. `WATERFALL_NAME_W` (20) and `WATERFALL_SUFFIX_W` (20, the ` 12.345ms STATUS` column) stay fixed so both pipes stay column-aligned. The row prefix is `marker(1) + name(20)`. A `WaterfallRow` keeps `marker`/`indent`/`name` *separately* rather than one pre-baked prefix string, because the name column is laid out at draw time (see the sticky-waterfall entry): the indent is written verbatim and the name is clipped into whatever cells it leaves. Two consequences of ever rendering deep traces, neither visible until a fixture nested past depth 4: the indent shares the 20-cell column at two cells per level, so the *rendered* indent is floored to keep the name `WATERFALL_MIN_NAME_W` (10) cells (see the relative-indent entry — depth itself is stored uncapped); and truncation must not introduce a non-ASCII glyph, so `clamp_field` became `clip_field(text, width, offset)`, marking clipping with ASCII `<`/`>` written *into* an edge cell rather than stealing width (the field stays exactly `width` cells, which is what the axis alignment rests on, and the `--ascii` guarantee holds by construction rather than by a flag). The column also scrolls horizontally following the cursor — offset `0` whenever the selected name fits, every row clamped to its own maximum useful offset so none scrolls into an empty field, and the **indent never scrolls**, since it is the only thing showing the trace's shape. The pane renders borderless via `Block::default().title(...)`, but ratatui 0.30 (`ratatui-widgets-0.3.2/src/block.rs`) reserves a top row for a title even with `Borders::NONE` (`Block::inner` insets when `borders.intersects(TOP) || has_title_at_position(Top)`), so a borderless-but-titled pane does not overlap its first content line. Master-detail: the waterfall is a *separate* async task keyed by `(query generation, selected trace id)`, applied to `snapshot.detail` only if both are still current on arrival (`Update::Waterfall`); the query snapshot ships a `"Loading..."` placeholder so the split layout is stable; `apply()` clears `detail_trace_id` so a refresh re-fetches the selected trace and the cursor keeps following the selection. Each trace row shows its start time: `"{trace_id}  {YYYY-MM-DD HH:MM:SS.mmm}  selected=…"` — `start_time_ns` was threaded through `TraceQueryMatch` (`imbh-lgtm`, populated from `SemanticTrace.start_time_ns` at the existing `result.push`, no second fetch) and rendered with `format_timestamp_ns`. The trace id MUST stay the leading whitespace token (`App::selected_trace_id` and `focus_select_trace` resolve the row by `split_whitespace().next()` — the row *is* the data model for waterfall selection), so the timestamp is appended, never prepended. `trace_matches_to_batch` (SQL/FFI projection) was deliberately left at two columns; carrying a struct field the Arrow projection drops is fine.

**Trace detail and span detail routes.** The half-height preview pane on the Traces list does not scroll, so a trace used to dead-end there. Two full-content routes fix that: `Route::TraceDetail` (header — trace id, span count, duration, start, with root service/operation in the block title — plus the whole waterfall as a span-selectable `List`, and, when the content area is ≥ `TRACE_DETAIL_SUMMARY_MIN_ROWS` (18) rows, a summary of the span under the cursor) and `Route::SpanDetail` (one span's full fields, scrolled like the log detail). `Enter` on the Traces list opens the trace detail, `Enter` on a waterfall row opens the span detail, and `L` from either opens Logs correlated by trace id **and** span id — the per-span drill-down that the earlier trace-granular `L` left open. **No extra query**: the list already materializes the selected trace for its preview pane, so `build_trace_detail` emits the `Waterfall` rows plus an aligned `Vec<SpanRecord>` in one pass and the app retains it (dropped as soon as the row cursor moves; an `Enter` that beats the in-flight fetch opens when it lands, via `pending_trace_open`). The preview pane still does not scroll but now titles itself `Waterfall: N of M spans — enter: all` rather than silently cutting deep traces.

**Sticky waterfall + a horizontally scrolling name column.** The trace detail pins the selected span's scrolled-off ancestors at the top of the pane, dimmed (`s` toggles, on by default; the state is an `App` field beside `show_mascot` and deliberately *not* in `NavEntry` — a display preference should survive Back/Forward, not be captured by it). `sticky_layout(rows, cursor, viewport, enabled) -> StickyLayout { pinned, offset, height }` is pure, so the geometry is testable without a terminal; the renderer splits the block's inner rect into a pinned `Paragraph` and a `List` with an explicit `ListState::with_offset`. **Anchor the pinned set on the cursor's ancestor chain, not the topmost visible row.** Pinning shrinks the window, which moves the offset, which changes whose ancestors you pin — a fixpoint. Anchored on the top row that function is *not monotone* and provably cycles (`A / B(child of A) / C(child of B) / D(root)` runs `1 → 2 → 0 → 1 …`), so any iteration budget gives a budget-dependent answer and the block flickers as the user holds `↓`; anchored on the cursor it is monotone on `{0..=cap}` and settles in ≤ `cap + 1` steps. The two anchors coincide *only* because the offset is stateless (a fresh `ListState` each frame ⇒ either `offset == 0` or the cursor sits on the last visible row); if it ever becomes stateful the anchor must be revisited. The pinned block caps at a third of the viewport, keeping the *innermost* ancestors. `WaterfallRow::parent_row` is a **row** index walked strictly upward — spans come back `ORDER BY start_time`, not as a tree, so clock skew can put a parent below its child, and walking upward is what makes the walk both correct and cycle-safe without a visited set. General rule: when a layout quantity feeds back into the geometry that produces it, the anchor decides whether the recursion is a fixpoint or an oscillator — choosing the anchor that makes it monotone beats any iteration cap.

**De-emphasis needs a channel the terminal actually honours, and `Modifier::DIM` is not it for box-drawing glyphs.** Pinned rows first used DIM alone; the name and duration dimmed while the `━` bar stayed at full intensity. Many terminals draw box-drawing characters *procedurally* — from a built-in geometry renderer rather than the font — and that path honours the cell's foreground colour but ignores the faint attribute. Verified by dumping `buffer[(x, y)].modifier` across a whole pinned row: every cell including the bar carried `DIM`, so it was never a code bug. The fix rides three channels: an explicit `fg` (`DarkGray`; errors keep `Red`, since a failing ancestor is still worth seeing), a lighter bar glyph (`Waterfall::light_marker`, `─`/`-` against `━`/`#` — both EAW-ambiguous in exactly the same way, so substituting one for the other cannot shift the axis), and `DIM` for terminals that do honour it. General rule: an attribute-only visual distinction is a bet on terminal support; carry anything load-bearing on colour or on the glyph itself.

**The divider under the pinned block is an `UNDERLINED` attribute on the last pinned row, not a rule row** — a `───` line would cost a viewport row out of a pane whose whole problem is being too short. It must be padded to the pane's full inner width: a waterfall line stops after its duration column, several cells short of the right border, so an unpadded row leaves the rule stopping short of the edge, where it does not read as a rule at all. Any full-width row styling has this requirement; `Paragraph` does not pad for you.

**Indent relative to the shallowest row on screen, not to the trace root.** Scrolled deep into a subtree, every visible row carries the same leading indent — it distinguishes nothing and spends the whole name column saying it. `visible_indent_base` takes the minimum indent across the rendered rows (pinned ∪ the scrolling window) and `render_waterfall` subtracts it, so the outermost visible span sits flush against the column and the rows below keep only their offsets *relative* to it; at depth 5 that hands ten cells back to every name. Anchored on the shallowest **rendered** row rather than literally the topmost: they are the same row in the usual case (the pinned block is the cursor's ancestor chain, ordered outermost-first), but a shallower sibling scrolling into the window underneath would otherwise need a negative shift, and clamping that at zero would collapse two different depths onto one column. It also **replaced** the absolute cap that preceded it. That cap flattened every trace past level 5 in the row model itself, whether or not the flattening bought anything, and it was the wrong instinct: it treated *depth* as the problem when the problem was only ever depth **shared** by the rows you can see. Depth is now stored whole and the only remaining bound is `WATERFALL_MIN_NAME_W` (10), a floor on the *rendered* indent applied after the base is subtracted — so it binds only when the rows visible together genuinely span more than five levels, instead of on every deep trace. General shape: prefer clamping a derived, view-dependent quantity at draw time over truncating the underlying fact at build time; the model should not lose information the view merely cannot show today. The draw-time parameters (`bar_cells`, `name_offset`, `indent_base`) travel as one `WaterfallView` named-field literal rather than a growing argument list, the same shape `SpanSpec` uses in `gen-demo-db`.

**Assert styling across the whole row, not one cell.** The first version of the pinned-row render test sampled `buffer[(2, y)]` — one cell in the name column — and so passed happily while the bar rendered at full intensity. A styling test should quantify over every non-blank cell of the row.

**Adaptive time-window narrowing for the trace cap.** Root cause of frequent "TraceQL source traces limit exceeded": the trace cap (`EvalLimits::max_traces`, wired to `max_rows` = 100) is enforced on the *candidate* traces for the window *before* the TraceQL predicate is evaluated (`imbh-lgtm/src/source.rs` `fetch_complete_traces` errors when `summaries.len() > max_traces`); `build_trace_query` pushes only time bounds + `limit(max_traces + 1)` into `TraceQuery`, not the span predicates, so a busy window overflows regardless of how selective the query is (adding `{ status = error }` does not help). Mitigation (TUI-only): `execute_traceql_adaptive` tries the full window, then progressively narrower sub-windows anchored at `end` (halving the span, `narrowing_starts`), rendering the most recent sub-window that fits with a loud banner + a `TraceQL (narrowed)` title. Results stay exact for the shown window (a transparent, reported reduction, not an invisible subset); a failed attempt costs only one candidate `search`, so ≤7 retries are cheap. If even the smallest overflows, `trace_limit_message` returns actionable guidance. Follow-up (semantics layer, out of TUI scope): push TraceQL span predicates down into the candidate `TraceQuery`.

**Log viewer detail + log→trace navigation.** Rule of thumb for master-detail: parse the row text for a single opaque key, but carry a structured payload when the detail is rich. Logs need severity, service, span id, body, and attribute/resource/scope maps, so `Snapshot` gained `log_records: Vec<LogRecord>` aligned to the selectable rows (`log_records[i]` ↔ `lines[list_from + i]`). No new facade API was needed: `LogEntry` already carries `trace_id: Option<TraceId>` / `span_id: Option<SpanId>` / `attributes|resource|scope: Attributes` / `severity_number: SeverityNumber`, all re-exported from `imbh`. `AnyValue` has no `Display`; a small recursive `render_value` (bytes→hex, arrays/maps compacted) covers all variants. A "focus overrides selection" field cleanly models cross-signal navigation into a selection-driven pane: jumping from a log to its trace sets `App::focus_trace_id`, switches to Traces, re-runs the query; `request_waterfall` prefers `focus_trace_id` over the row selection so the focused trace shows even when absent from the current result; after the result lands, `focus_select_trace` moves the cursor onto the matching row and clears the focus; any cursor movement also clears it, and `switch_screen` drops a stale focus when leaving Traces. `Mode::LogDetail` renders via an early `draw` branch (`draw_log_detail`) with its own nav/body/hint layout, reusing the `App::scroll` + `max_scroll`/`page_rows` cells (free because the Logs list is a `List`, not scroll-based); being non-`Normal`, it pauses auto-refresh so the viewed record stays stable.

**Metrics catalog tree + checkbox query builder + catalog→query drilldown.** Read groupable dimensions off a metric's series *labels*, not `series()`: `metrics().series(m)` omits the resource `service`, but the PromQL executor's `metric_labels` (`imbh-lgtm/src/source.rs`) folds `service` into every series' label set alongside data-point attributes (`__name__`/`le` are internal), so running the bare selector and reading `PromSeries.labels` surfaces exactly the queryable dimensions, guaranteed to match what `sum by (…)` groups on. Make discovery time-range independent by anchoring at the data, not `now`: `db.stats()` exposes each metric table's `min/max_time_unix_nano`; discovery evaluates the bare selector as a single instant at `span_end + 1` with `lookback_ns = span_end − span_start` (the PromQL fetch scans `[range.start − lookback, range.end]`, `plan_prom_fetch`), so it scans the whole retained span regardless of the picker; only the *visualization* query (built on `Enter`) uses the picker window. A plain selector (not a `rate`) is used for discovery so it doesn't depend on samples landing in a rate window. The tree (`metric_tree` with lazy `dims`) is flattened each change into the existing `Snapshot::table` plus `tree_rows: Vec<TreeRowRef>` mapping each visible row to a `Metric/Dim/Value` node, reusing the table render + cursor. Exclusive-per-axis checkboxes are one `Option<usize>` per dimension (`DimNode::selected`, radio within the axis, toggle-off on re-select); checked values across axes become `{label="value",…}` matchers; a single `build_metric_query(name, kind, matchers, group_by)` covers whole-metric / filtered / grouped for all kinds (the grouped axis is dropped from matchers as redundant). Catalog→series drilldown is pure query state, no new mode: `Enter` on a catalog row sets `active_query_mut()` to `default_promql` and calls `request_refresh`; `load_snapshot` already branches catalog-vs-series on query-empty (query-empty ⟺ catalog), so the view flips for free; `Esc` clears the query back to catalog. The metric kind is read from the selected row's `Kind` cell (controlled-format row-parsing).

**Metrics tables.** A third primary-pane render mode (table → list → plain-scroll) slotted in behind one accessor: `App::selected` is 0-based into `table.rows` for a table, absolute into `lines` (offset by `list_from`) for a list, but they never mix (a screen is only ever one mode, `selected` resets on switch). Centralizing both in `selectable_bounds()` (returns `(0, rows-1)` for a table, `(list_from, len-1)` for a list) meant `move_selection`, the `apply()` clamp, and reset logic needed no changes — fold a new view mode into the one bounds accessor the input layer already consults. Selection-driven scrolling comes from building a fresh `TableState`/`List` each frame with only `select(Some(i))` (offset 0), which makes ratatui auto-scroll to keep the selected row visible — no manual offset/scrollbar state. `ratatui::widgets::Cell` shadows `std::cell::Cell` (the interior-mutability type used for scroll-bounds handoff): never import the widget `Cell`; `Row::new` takes `IntoIterator<Item: Into<Cell>>` and `String`/`Line: Into<Cell>`, so pass cell strings/lines directly.

**Time-series viewer + multi-metric visualization.** Retain the raw series to build a detail view — a rendered summary row is lossy. The Metrics table showed Series/Latest/Min/Max/Points and plotted only `series.first()`; a detail viewer for an *arbitrary* selected series needs the per-series `(timestamp_ns, value)` history kept alongside, so `Snapshot` carries `series: Vec<SeriesData>` aligned to `table.rows` (the same pattern as `log_records`); clone the selected one into `App` on open so it survives a background refresh. A movable x-cursor on a ratatui `Chart` is just a second line `Dataset` with two points `[(cx, y_min), (cx, y_max)]` in a contrasting colour (the widget renders internally, no per-cell overlay hook); the exact reading goes in a separate text readout. Keep the plot off the borders by padding y-bounds (widen a flat line to `±1`), and reuse `page_rows` (published from `draw`) to page the cursor by a screenful of plot columns. Multi-metric: check the executor's grammar before designing a "combine N things" feature — IMBH `PromExpr` has only `Selector`/`Rate`/`Aggregate` (no binary `or`/`and`), and `exact_metric_name` *requires* an exact `__name__` matcher (so `{__name__=~"a|b"}` is rejected). The only correct path is multi-query execution — run each metric's query independently and concatenate result series (each keeps its `__name__` via `metric_labels`). Multiple queries ride the single-query pipeline via a `\n` join (a newline can never appear inside a PromQL query, so it is a safe in-band delimiter); `load_snapshot`'s Metrics branch `split('\n')`s, runs each, concatenates; `highlight_query` renders each `\n` as a dim ` │ ` separator. Don't add a selection gesture when existing marks carry the intent: the first cut added an explicit metric-level checkbox on key `x`; user feedback favoured *implicit* selection — any metric with ≥1 checked series (`DimNode.selected`) is visualized, each filtered by its own checked values, cursor node the fallback when nothing is checked. But an implicit-from-a-child-signal selection strands nodes with no such child: dimensionless metrics have no series to check, fixed by a `whole_selected` flag surfaced as a checkbox on the `(no dimensions)` placeholder row with its own `TreeRowRef::NoDims(mi)` (so `Space` toggles the box instead of collapsing the metric). General rule: when selection is derived from a per-child mark, audit the zero-children case and give it an explicit affordance.

**Absolute/interactive time-window selection.** Rolling vs absolute is one branch at the window-derivation seam, not a parallel path: adding `Options.window: Option<(i64, i64)>` (public, and settable at launch via `--from`/`--to`, both-or-neither and ordered) and branching in `eval_window` (absolute span verbatim vs `now - lookback .. now`) means metrics sampling, trace/log bounds, and catalog visualization all pick up absolute windows for free. The step for an absolute span is *derived* (~120 points, whole seconds, `>= 1s`) so `max_samples` stays bounded. A fixed window must be re-applied on every refresh or it silently reverts to rolling: `request_refresh` rebuilds `Options` each time and must copy `options.window = app.abs_window` alongside `lookback`/`step` — the upside is intended semantics (refreshing an absolute window re-queries the *same* span, surfacing late-arriving data). Hand-rolled UTC parsing needed `days_from_civil` (Y/M/D→days), the companion of the existing `civil_from_days`; round-trip is the cheap correctness check (`parse_datetime` ∘ `format_datetime_ns` is identity on whole-second instants). A side-effecting `match` guard is how clippy wants a "run-always, act-on-success" arm written: `KeyCode::Enter if commit_absolute() => refresh()` (the guard runs validation for its side effect every time, the arm body fires only on `true`) — written as `Enter => { if commit() { refresh() } }` it trips `clippy::collapsible_match`. Both the preset dropdown and the absolute-range form anchor to a `Rect` computed in `draw` and passed into `draw_*`, clamping on every side (no stored geometry needed, unlike the scroll bounds that cross from `draw` back to the key handler); the `Absolute…` picker row is the last selectable index (`range_cursor` ranges `0..=TIME_RANGES.len()`). A live clock needs a redraw heartbeat that must not become a refresh heartbeat: cap the idle sleep to 1s so the clock ticks, but gate the actual refresh on `last_refresh.elapsed() >= refresh_interval` inside the timer arm — wake cadence and refresh cadence independent.

**Pan/zoom + log paging + cross-signal drill-down + small-terminal.** `[`/`]` pan the window earlier/later by half its span; `-`/`+`(`=`) zoom out/in 2x about the center. `App::pan_window(fraction)` / `zoom_window(factor)` freeze the effective window to an absolute span (panning stable against the wall clock), clamp the span to `[1s, ~1y]`, and never pan the leading edge past `now`. Pan-*later* that reaches `now` clears `abs_window` (resumes the live rolling window) — "reached now" must mean "resume live", not "stop here" (an absolute pin that silently stops tailing reads as broken); the header flips back to `last <preset>` as the "you're live" cue. `n`/`p` page the Logs list via the facade's opaque `PageCursor` (no public constructor, so paging state can only be *carried* — an `App::log_cursor_stack` + `log_next_cursor` echoed from each `LogPage.next` through `Snapshot.next_cursor` — never *computed*, which is why `request_refresh` resets to page 0 on every non-paging refresh, the single spawn point); offset paging is coherent only against a fixed query/window; the volume sparkline is built from an unpaged clone taken before `.after`. `L` opens Logs filtered to the selected trace via the facade filter `LogQuery::trace_id(TraceId)` / `span_id(SpanId)` (trace-granular from the Traces list; span-granular from the trace/span detail routes, which supply a span id too) (`crates/imbh/src/logs.rs`; raw-binary `X'…'` equality, injection-safe machine hex inlined not bound, bloom-prunable like `traces().get`); held in `App::log_correlation`, layered on in `load_snapshot`, captured by nav history (Back restores it), cleared on leaving Logs or a fresh query. Metric-exemplar→trace: opening a metric detail fetches `db.metrics().exemplars(name)` off-thread (`request_metric_exemplars`, guarded by labels+query so a stale fetch is dropped); the name comes from the series' `__name__`, else `metric_ident_from_promql` (a small selector extractor that skips aggregation ops, `by(…)` lists, and function calls, recovering `name`/`name_bucket` from the shapes `build_metric_query` emits); trace-carrying exemplars in the plotted window become magenta floor dots, `Enter` jumps to the trace of the marker nearest the chart cursor (`nearest_exemplar_trace`). Below `MIN_COLS`×`MIN_ROWS` (40×10) `draw` renders a centered "Terminal too small / Resize to at least 40x10 / (now WxH)" prompt (the floor kept at/under the smallest size the existing render tests exercise, 48×10). Three interactive-only defects on the metric-detail chart all traced to *the same root cause — a domain-widening edit not swept against every consumer*: (1) pan/zoom "did nothing" because `Route::MetricDetail` rendered `detail.points` cloned at open time — fixed by re-deriving points from the matching series (by label set) in `App::apply` on every fresh Metrics result (a series that left the window clears the plot honestly); (2) that let `points` become *empty*, and `draw_metric_detail` indexed `points[cursor]` unconditionally → panic — fixed with `points.get(cursor)` + a "no samples in this window" line; (3) pan-later awkwardness (above).

### Rendering and the mascot

**East-Asian-width-safe glyphs and markers.** See Pitfalls for the full width discipline. Disclosure markers went ▼/▶ → the neutral ▾/▸ → finally the unconditional pure-ASCII `v`/`>` (the small triangles render too small to read; the full-size ones are EAW-ambiguous). `BRANCH_MARKERS` in `draw_metric_table` is `["v ", "> "]`. Colour a sub-token of a table cell by splitting it into a `Line` of spans (leading `indent + marker` in `DarkGray`, remainder default), gated on `App::on_catalog()` and matched against exact marker prefixes so checkbox/loading/series rows render unchanged. Don't pair a `▶` highlight symbol with tree rows that start with their own branch markers — drop `highlight_symbol` on every selectable list/table and rely on the reverse/bg row-highlight style (an unambiguous cursor that never collides with row content). The completion popup still uses an ambiguous `▶` highlight symbol (`draw_completion_popup`) — out of scope as a non-tree marker, but it carries the same EAW risk.

**Pure-ASCII `--ascii` mode.** A single `Glyphs::new(ascii)` bundle is the one source of truth for every chrome glyph, plus an `ASCII_BORDER` `ratatui::symbols::border::Set` (`+ - |`) and a `Glyphs::block()` helper every bordered `Block` routes through (Unicode `border::PLAIN` otherwise; ratatui ships no ASCII border set, so construct a `border::Set` literal with fields `top_left/top_right/bottom_left/bottom_right/vertical_left/vertical_right/horizontal_top/horizontal_bottom`). ASCII mappings: logo `⬤`→`*`, clock `⏲`→dropped, warn `⚠`→`!`, dash `—`→`-`, separator `·`→`|`, arrows `←→↑↓`→`<>^v`, ellipsis `…`→`...`, vline `│`→`|`. Only chrome is rewritten — log bodies, labels, and values are never touched. `Glyphs` is constructed in `draw`, `draw_global_overlays`, `draw_metric_detail`, and (because it builds the Traces truncation warning and em-dash titles) the async `load_snapshot`. The waterfall already gated its bar glyph (`━`/`#`) on `ascii`.

**The mascot "atta".** A decorative animated mascot from four-frame block-glyph art (`./assets/mascot.txt`; deliberately uneven leading whitespace makes the head/feet waddle). Not a pane, an overlay: a borderless `Clear` + 3-row `Paragraph` floated flush-right in the bottom-right corner with a one-column margin and two rows above the bottom, with a size guard that skips it entirely on a too-small terminal. Hidden by default (`App.show_mascot`, init `false`; `KeyCode::Char('m')` toggles); no mascot in `--ascii` (the art is inherently block glyphs). Animation with no timer thread: the frame index is derived purely from the wall clock (`mascot_frame(now_ns)` → `now_ns.rem_euclid(period*4)/period`, valid for pre-epoch instants), so `draw` stays a pure function of app state + clock; the event-loop wake tick drops from 1s to 200ms *only* while the mascot is visible (`show_mascot && mode == Normal && !ascii`). Exact glyphs are preserved by a codegen script that reads the art file rather than hand-typing block characters. The overlay draws first in `draw_global_overlays` (before the range/absolute pickers), and the completion popup draws after, so both pickers and the popup always paint on top. Later reworked into an **event-driven, pluggable motion system**: the run loop turns frame-to-frame state deltas into `MascotEvent`s (`Navigated { on_metric_chart }`, `Idle`/`Active`, `Refreshed { auto }`) and feeds them plus a tick to a `Mascot` controller. Motions are pluggable: a `MascotMotion` (advance body, return `false` when done) plus a `MascotIgniter` (arm on an event, poll each tick to fire); add an easter egg by pushing one igniter into `Mascot::new`. Because `draw` is `&App`, motion state advances in the run loop before the draw (which only blits `app.mascot.body`); render-time geometry flows back via `chart_geom: RefCell<Option<ChartGeometry>>`. Two motions ride it: `IdleWander` (intermittent left/right strolling, *only while idle* — the controller withholds ticks while the user is active, so the mascot rests during use, strolling only after ~3 s without a keystroke) and `ChartRide` (hop onto a chart's peak, then slide down the descending line). The chart-ride reproduces ratatui's `Chart` layout exactly (`ratatui-widgets 0.3.2`: graph area = `block.inner(area)` minus a left gutter = `max(y-label widths, first-x-label width − 1)` capped at `width/3`, +1 for the y-axis, and **2** bottom rows; Braille canvas maps a point to cell `(left + ⌊dot_x/2⌋, top + ⌊dot_y/4⌋)`, `dot = round(norm · (res−1))`, `res = (2w, 4h)`) via `chart_graph_area` + `chart_point_cell`. Slide lessons: a "slide" is only visible if densified and time-paced (`densify` to a one-cell-per-step polyline; descending runs are often 2-3 points and otherwise collapse to one frame — "all I see is it climbs up"); a peak is a local *row-minimum* with downhill on both flanks, so `great_displacement_path` searches both directions; prefer the gentle hill (smallest fall-per-column among drops ≥ `max(3, height/3)` rows — a cliff reads as falling, not sliding); velocity integrates `speed += (G·sin θ − F·speed)·dt` (`sin θ` smoothed over ±3 cells to dodge path quantisation, `pos` recomputed after advancing so a fast tick can't overshoot); facing is fixed once for the whole slide from the net peak→trough direction (recomputing per micro-segment flickers on vertical steps where `Δx == 0`). Stale render geometry can eat a one-shot trigger: the controller polls igniters at loop-top against the *previous* frame's `chart_geom`, so detail→detail left the old chart's geometry in place — fixed by clearing `chart_geom` on any route change and never spending the roll while geometry is absent. The 4 art frames already encode both facings (`1-a`/`1-b` rightward, `2-a`/`2-b` leftward), so `mascot_art(facing, phase)` just selects the pair. Ignition is per-event: arriving on a rideable chart rides at **0.8**, a background auto-refresh re-rides at **0.25**; manual refresh and non-chart navigation don't arm it. **Shift+←/→** are arrow-key aliases for the `MetricDetail` chart x-cursor (`metric_cursor`) alongside `h`/`l`, in `handle_detail_key` gated on `KeyModifiers::SHIFT`; the bare arrows are owned by the router (Back/Forward), so Shift is the modal-free escape hatch (`handle_detail_key` runs before the history-nav match, consuming Shift+arrows while plain arrows fall through). Shift+arrow reporting is terminal-dependent, so `h`/`l` remain the always-works fallback.

### gen-demo-db

`examples/gen-demo-db` populates an imbh database with realistic demo metrics, traces, and logs. Usage: `cargo run -p gen-demo-db -- <dir> [--minutes N] [--step-seconds N]`, then `cargo run -p imbh-tui -- <dir>`. Across 4 services / 2 hosts / 4 routes it emits a `cpu_utilization` gauge, a monotonic cumulative `http_requests_total` counter, and a cumulative `request_duration_seconds` histogram, plus traces and severity-varied logs. Deterministic via a fixed-seed splitmix64 PRNG (no `rand` subtree). Metric names use underscores so PromQL entry in the TUI is unambiguous (no dot→underscore escaping). Keeping it an example crate preserves the footprint budget — `opentelemetry-proto` + `prost` live only here (like `bench`/`rss-probe`), never entering the `imbh` facade graph.

**Demo data for the TUI must be anchored to wall-clock `now()`, not epoch.** The explorer builds every query range from `Timestamp::now()` minus a lookback window (`load_snapshot`), so `bench`-style tiny epoch-relative timestamps would land ~56 years before the window and render empty. The generator steps timestamps back from `now()` over `--minutes` — this is the whole reason the data is visible; any future demo/replay fixture aimed at the TUI has the same requirement. A same-process read-only reopen needs every `Db`/`BlockingDb` handle dropped first (the single-writer lock is held until the last strong `Arc<Db>` is dropped), so the generator does the write phase in an inner scope ending in `flush()` + `close()`, then calls `Db::open_read_only` on the same dir. `flush()` seals buffer → Parquet on disk, so a separate read-only process sees the data under any WAL mode (durability for a *different* opener comes from sealed segments, not the in-memory buffer). The built-in verification pass reopens read-only and counts rows per table via `BlockingDb::sql`, a cheap end-to-end durability check. Cumulative OTLP series (`aggregation_temporality = 2`) accumulate across the whole history in per-service `ServiceState` and only ever advance, so the counter/histogram are well-formed for the reset-aware rate/histogram math in `imbh-semantics`.

**Per-run id salting.** Trace/span ids were derived from a `span_seq` counter starting at `1`, so a second run into the *same* dir reused the previous run's ids at newer timestamps, corrupting earlier traces. Fix: seed the id sequence from the run anchor (`span_seq = now.max(1)`) instead of a constant. `trace_id`/`span_id` derive from `span_seq` via bijective hashing (n in the high bytes; odd-constant multiply), so run *k* occupies the disjoint id space `[now_k, now_k + spans)`; distinct runs are separated by seconds (~1e9 ns) — orders of magnitude more than the few hundred ids a run consumes. Design trade-off (user decision): "unique ids per run" over "enforce a fresh directory"; consequence is that identical-ids-every-run reproducibility is gone (fixed `now` still reproduces, but `now` moves). Verified: two runs into one dir → 60 span rows, `count(DISTINCT trace_id)=30`, `count(DISTINCT span_id)=60` (zero collisions).

**Correlating logs to real spans.** Log records now carry a valid, structured trace/span correlation instead of standalone plain text. The pipeline already supported it end to end (`imbh-otlp` `logs_request_to_rows` maps `rec.trace_id`/`rec.span_id` to `LogRow`, `imbh-storage` writes those into the `logs` table's `trace_id`/`span_id` columns) — only the generator omitted the ids. Design: derive logs from the step's spans, not independently. `traces_body` returns `(Vec<u8>, Vec<SpanRef>)` — the encoded body plus one `SpanRef { trace_id, span_id, service, route, is_error, is_root }` (later `Role`) per emitted span; the ingest loop generates traces first, then feeds the `SpanRef`s to `logs_body`, which emits exactly one `LogRecord` per span carrying that span's ids, grouped under the span's service resource, attributes mirroring the span. Body/severity stay self-consistent and keep the full-text path fed (`log_line`: error root spans → ERROR "request failed: upstream error" containing "error" so FT search still matches; healthy roots → INFO/occasional WARN). `logs_body` uses explicit `for` loops (not nested iterator closures) to keep the `&mut Rng` borrow simple and rng consumption order deterministic.

**Deepening traces into multi-level cross-service call trees.** Each trace is now 7 spans, max depth 3, spanning two distinct services:

```text
GET {route}            SERVER    entry
├─ authz.check         INTERNAL  entry
├─ rpc {downstream}    CLIENT    entry
│  └─ GET {ds_route}   SERVER    downstream   (second, distinct service)
│     ├─ db.query      CLIENT    downstream
│     └─ cache.get     INTERNAL  downstream
└─ db.query            CLIENT    entry
```

Time nesting is guaranteed correct, not hand-tuned: a `nest(start, dur, start_pct, dur_pct)` helper carves a child window out of its parent's as integer percentages (callers keep `start_pct + dur_pct <= 100`), so every child is strictly inside its parent's `[start, end]` without brittle absolute-offset arithmetic (0 dangling parents verified). Cross-service is real: the `rpc` CLIENT span's child is a SERVER span emitted under a *different* `service.name` resource (picked distinct via `(entry_idx + 1 + below(len-1)) % len`), both sharing the trace id (every trace has exactly 2 distinct services). Error propagation mirrors a bubbled-up failure: ~1 trace in 8 fails, originating at the downstream `db.query`, its ERROR status propagating up only the calling path while sibling branches stay OK (of 20 ERROR spans, 0 had a non-error ancestor on their parent chain). Construction is factored through a `SpanSpec` named-field literal + `build_span(trace, spec)` (avoids a 9-arg call / clippy `too_many_arguments`); `bump(&mut seq)` consumes id-sequence values; span ids still come from the wall-clock-salted `span_seq`. Logs follow the richer tree: `SpanRef.is_root: bool` became a `Role` enum (`Entry`/`Authz`/`Rpc`/`Downstream`/`Db`/`Cache`) that `log_line` and the log attribute switch on. Still one correlated log per span (a 2-minute run: 189 spans / 189 logs, all with a `span_id` matching a real `(trace_id, span_id)`, 0 dangling).

### Terminal lifecycle: one restore path plus a chained panic hook

Terminal setup is not atomic — `execute!(EnterAlternateScreen, Hide)` can succeed on the first command and fail on the second, and the original error branch only disabled raw mode, leaving the user in a live alternate screen with no TUI drawing into it. Every exit path (normal teardown, `enter()`'s own error branch, panic) now funnels through one **`restore_terminal` helper**: leave the alternate screen, show the cursor, disable raw mode — in that order, and unconditionally, since each step is harmless when it was never applied.

A **panic hook** is installed on top: it restores the terminal *before* delegating to the previously installed hook, so the panic message and backtrace print on the normal screen instead of vanishing with the alternate screen. Two properties make it safe to install from a library-ish crate: it is **chained** (captures and calls the prior hook rather than replacing it), and it is **idempotent** — an `AtomicBool` compare-and-swap guards installation so repeated `enter()` calls do not stack hooks that each restore and each delegate. The extracted pure helpers carry two focused unit tests; the `execute!`-driven parts are exercised only by reading, per the standing terminal-free testing caveat.

## Test Coverage

- The `imbh-tui` unit suite is pure-`App` and terminal-free where possible; render tests use `ratatui::backend::TestBackend` (available under `default-features = false` + `crossterm_0_29`). Grew roughly 30 → 116 across the work. There are no `dev-dependencies` and no snapshot testing — a snapshot crate would trip the footprint gate; render tests flatten the buffer and assert substrings (never full-buffer equality), always under `Options { ascii: true, .. }` so Unicode chrome cannot pollute the match.
- **Render tests prove structure, not legibility.** Two sticky-waterfall defects produced perfectly well-formed rows and passed every substring assertion, yet were wrong *as a picture*: pinned ancestors (the shallowest rows, so usually the shortest names) scrolled clean out of their own field and the context band rendered blank; and scrolling the column shifted the indent off the left edge, so the whole trace shape vanished. Both were found only by driving the real binary against a `gen-demo-db` database in a **sized pty** — `script` gives a 0×0 window and the TUI renders nothing, so the harness needs `pty.fork` + a `TIOCSWINSZ` ioctl. Worth reaching for whenever a change is about *layout* rather than content.
- A geometry fixpoint deserves a counterexample test, not just a happy-path one: `sticky_layout_is_stable_across_a_subtree_boundary` asserts the invariants at *every* cursor value over exactly the shape that makes the naive anchor cycle. A 20 000-case fuzz over random forests confirmed cursor-visibility, pinned-above-window, and the cap.

## Pitfalls

- **Terminal width / East-Asian glyphs.** Fixed-width text columns must clamp/measure by *display width* (`unicode-width`: `UnicodeWidthStr::width` / `UnicodeWidthChar`), never `char`/scalar count — a full-width CJK glyph like `データベース照会` is 8 `char`s but 16 cells, so padding by `char` count throws a monospace column (and any waterfall axis) off by one cell per wide glyph. `clamp_field` pads to the cell count, truncates by accumulating widths and stopping before a glyph overflows the `width−1` budget, then appends `…`; a wide glyph straddling the last cell is dropped and space-padded so the field is *exactly* `width` cells (the trailing pad space after `…` is what preserves alignment — the test asserts `contains('…')` + exact width, not `ends_with`). ratatui's *per-cell rendering* is width-aware but *column allocation* (`Constraint::Length`) is not unless you feed it `UnicodeWidthStr::width` — the two must agree or wide content clips.
- **Box-drawing is the deliberate exception to the EAW rule — do not "fix" it.** Every glyph in ratatui's default `border::PLAIN` set is ambiguous (`│ ─ ┌ ┐ └ ┘`, `width` 1 / `width_cjk` 2), and so is the waterfall's `━`/`─` bar. That is not an oversight and not a latent bug: ratatui's whole cell grid assumes ambiguous-as-narrow, as does essentially every terminal UI framework, so a terminal configured ambiguous-as-2 breaks *any* box-drawn TUI — which is why CJK users generally set ambiguous-width to 1. Fixing the bar alone would be incoherent (the frames around it have the identical property), and there is no drop-in replacement anyway: probing 23 candidates found the entire box-drawing **and** block-element repertoire ambiguous (`━ ─ ═ ┄ █ ▄ ▀ ▂ ▁ ■ — ― ‾`), leaving only `▬ ╌ − ⎯ ⸺ ¯ ‗` and ASCII — none of which look like the current bar. `--ascii` is the supported escape hatch for a terminal that cannot do box drawing. The rule below is about something narrower.
- **Decorative glyphs in a line whose width *we* compute must be EAW-unambiguous.** This is the actual scope: accent glyphs sitting inside strings our own alignment arithmetic measures (the menu-bar brand and its right-aligned clock, hint separators, tree markers) — not chrome ratatui lays out on its grid. A char is ambiguous exactly when `UnicodeWidthChar::width(c) != width_cjk(c)` — 1 in Western context, 2 in a CJK locale. `UnicodeWidthStr::width` (the layout math) returns the *narrow* value, so an ambiguous glyph a CJK terminal renders as 2 cells desyncs the whole bar by one cell. Avoid `●` U+25CF, `•` U+2022, `·` U+00B7, `▼` U+25BC, `▶` U+25B6. Safe: `⬤` U+2B24, `⏲` U+23F2, `▾` U+25BE, `▸` U+25B8 (all `width == width_cjk == 1`). Verify with a throwaway `unicode-width` probe printing `width` vs `width_cjk`; pin the exact codepoint in a comment (`U+2B24 not U+25CF`) so a later "prettier" swap doesn't silently break alignment. A rendered glyph chosen for its width often has a second copy in width-math or matching code (marker strings, `BRANCH_MARKERS`, comments) that must move together.
- **`draw` is `&App`; publish render-time bounds back, don't recompute in the handler.** Any bound only the renderer can compute (wrapped-row count, viewport height, chart datapoint cells) must be published through interior mutability (`Cell<u16>` for `max_scroll`/`page_rows`, `RefCell<Option<ChartGeometry>>` for `chart_geom`) and read by the key handler — safe only because the loop is single-threaded. Motion/scroll state advances in the run loop *before* the draw. A dropdown/form that anchors to a box computed in the *same* `draw` pass needs no `Cell` (the anchor `Rect` is a local), unlike bounds that cross from `draw` back to the handler.
- **Small terminals.** Below 40×10, `draw` renders a centered resize prompt instead of the paned layout; overlays (mascot) size-guard and skip rather than collide with the status/hint bar. Keep the floor at/under the smallest size the render tests exercise (48×10) so those still paint the real UI.
- **Live vs pinned windows.** An absolute (`abs_window`) window is frozen and never tails new data; it must be re-applied on every `request_refresh` or it silently reverts to rolling. A forward-panning time control that reaches `now` should *resume live* (clear `abs_window`), not pin an absolute window at that instant — a silent stop reads as broken. Auto-refresh over an absolute window is a no-op, so the `!` "will keep advancing" flag is gated on `abs_window.is_none()`. A detail route is a frozen clone by design (to survive background refreshes), so its chart can go stale unless `App::apply` re-derives its points from the matching series each refresh — and a domain-widening edit like that (points can now be empty) must be swept against every consumer that assumed the old invariant (`points[cursor]` → `points.get(cursor)`), or the crash surfaces two functions away.
- **Read-only handle accessors.** A read-only `Db` (`open_read_only`) holds no live in-memory state; anything reading `storage.inner` directly (e.g. a naive `Db::stats()`) reports the empty shell (`rows=0 segments=0`) even while queries in other panes return data. Every writer-side accessor (`stats`/`buffer_bytes`/`wal_bytes`) needs a reader-aware path that reads the manifest and replays the WAL tail into a scratch `Storage`. The tell: data visible in queries but not in stats. Regression tests must exercise both the never-sealed (all rows in WAL tail) and sealed (rows in segments) states, since a short-lived demo DB often never crosses the seal threshold.
- **Terminal setup is not atomic, so the error path must restore everything.** `execute!(EnterAlternateScreen, Hide)` can partially apply; an error branch that only disables raw mode strands the user in a live alternate screen. Restore unconditionally (leave alt screen → show cursor → disable raw mode) from a single helper used by *every* teardown site, and install a chained, CAS-guarded panic hook so a panic message prints on the normal screen. Un-chained or re-installable hooks are the two ways this goes wrong.
- **crossterm key quirks.** Shift+letter arrives as the uppercase `KeyCode::Char('R')` (match the uppercase char, not `Char('r')` + a SHIFT check). Shift+arrow reporting is terminal-dependent (modern terminals + crossterm deliver `KeyCode::Left/Right` + `KeyModifiers::SHIFT`, older ones don't distinguish it), so keep an unmodified fallback (`h`/`l`) rather than replacing it.
- **`gen-demo-db` gotchas.** Timestamps must anchor to wall-clock `now()`, not epoch, or the TUI window shows nothing. Drop every `Db`/`BlockingDb` handle before an in-process `open_read_only` on the same dir. `flush()` before exit so a separate read-only process sees sealed segments. Seed `span_seq` from the run anchor so repeated runs into one dir don't collide ids. `logs_body` must use explicit `for` loops to keep `&mut Rng` borrows simple and rng consumption order deterministic.
